## 1. Context

Codebasics uses **Microsoft Clarity** for behaviour analytics on its web application. Clarity only shows rolling data and sends a weekly summary email (rage clicks, dead clicks, quick backs, JavaScript errors, total sessions, pages per session, scroll depth, session duration). We want our **own daily history** of these metrics so that we can track trends over any period.

The app, **Clarity Insights**, has three responsibilities:

1. **ETL pipeline:** fetch data from the Clarity Data Export API once a day and store it in PostgreSQL.
2. **Pipeline monitoring UI:** show every pipeline run with its start time, end time, data retrieved, and failure reason.
3. **Analytics dashboard:** show KPI cards for any selected period, plus a line chart with metric and dimension filters.

The app is deployed to our own hosting platform. A **cron job on that platform** triggers the ETL. Users sign in with **Microsoft (Entra ID)**.

## 3. Microsoft Clarity Data Export API: facts and constraints

- **Endpoint:** `GET https://www.clarity.ms/export-data/api/v1/project-live-insights`
- **Auth header:** `Authorization: Bearer <CLARITY_API_TOKEN>` (generated by a project admin under *Settings → Data Export*).
- **Query params:**
  - `numOfDays`: `1`, `2` or `3`. The last 24, 48 or 72 hours **counted back from the moment of the call**. Any other value returns HTTP 400 with an empty body. **This app always uses `1`.**
  - `dimension1..3`: optional breakdowns. Allowed: `Browser`, `Device`, `Country/Region`, `OS`, `Source`, `Medium`, `Campaign`, `Channel`, `URL`.
- **Hard limits:**
  - **10 requests per project per day.** HTTP 429 = limit exceeded. The limit **cannot be raised** and is **shared** with every other tool on the same project.
  - At most **1,000 rows** per response.
  - A `numOfDays=2/3` call returns **one total for the whole window**, not one row per day.
  - History beyond 3 days is not retrievable. **A missed day that is not recovered the same day is lost forever.**
- **Response shape (verify against a real response):** a JSON array of metric objects:
  ```json
  [
    { "metricName": "Traffic",
      "information": [ { "totalSessionCount": "1234", "totalBotSessionCount": "10", "distinctUserCount": "900", "pagesPerSessionPercentage": 2.14, "OS": "Windows" } ] },
    { "metricName": "DeadClickCount",
      "information": [ { "sessionsCount": "...", "sessionsWithMetricPercentage": 6.7, "subTotal": "..." } ] }
  ]
  ```
  Expected metric names include `Traffic`, `EngagementTime`, `ScrollDepth`, `PopularPages`, `DeadClickCount`, `RageClickCount`, `QuickbackClick`, `ExcessiveScroll`, `ScriptErrorCount`, `ErrorClickCount`, among others.
  **The field list is not hardcoded as the only truth.** Numbers often come back as strings. The parser must:
  - store the full raw response,
  - flatten generically (every numeric-looking field becomes a row),
  - treat dimension keys present in `information[]` as dimension values,
  - log, without failing, unknown metrics or fields that cannot be parsed.

## 4. ETL pipeline requirements

### 4.1 Triggering

Two entry points share the same core service:

1. **CLI script:** `npm run etl:run`. The primary path for the hosting platform's cron, e.g. `30 0 * * *` IST (00:30 daily).
2. **HTTP endpoint:** `POST /api/etl/run`, protected by `Authorization: Bearer <CRON_SECRET>`, for platforms where cron can only call a URL. Returns `202` with the `runId` and runs the job to completion in the background. The README documents the host timeout implications.

**Manual runs** from the UI are admin only. The UI shows how many API calls are left in today's budget before confirming.

### 4.2 Pull configuration

Pulls are defined in a typed config file (`src/etl/pulls.config.ts`) and seeded into the `pull_configs` table, which is what the ETL reads. Each pull is one API call with `numOfDays=1`.

| key | dimensions | purpose |
|---|---|---|
| `overall` | none | Site-wide KPIs (matches the weekly email) |
| `device` | `Device` | Mobile vs. desktop |
| `source_medium` | `Source`, `Medium` | Traffic channel quality |
| `url` | `URL` | Page-level frustration hotspots |

- Each pull has `enabled: boolean`.
- Default usage: 4 calls per scheduled run, leaving 4 spare under the scheduled cap (10 − 2 reserved = 8).
- **No backfill.** History starts on the first successful run. (Removed in v1.1: a 3-day call returns one 72-hour total that cannot be split into reliable daily values without 3 calls per pull, and it adds only 2 days of history once.)

### 4.3 API call budget guard

- Every outgoing Clarity call, retries included, is logged in `api_call_log`.
- Calls are counted per **budget day**: the IST calendar date, shifted by `CLARITY_BUDGET_RESET_OFFSET_MINUTES` (default `0`, i.e. IST midnight). Clarity's real reset time is not documented, so the boundary is configurable.
- Env `CLARITY_DAILY_CALL_BUDGET` (default `10`) and `CLARITY_RESERVED_CALLS` (default `2`, kept free for retries, manual late runs and other tools).
- Before each call of a **scheduled** run: if `used + 1 > budget − reserved`, skip the remaining pulls and mark them `SKIPPED_BUDGET` (`error_code = BUDGET_EXHAUSTED`).
- **Manual** runs may use the reserved calls, but only after an explicit confirmation that shows the remaining budget. Never more than `budget` in total.

### 4.4 Run semantics

- **Concurrency:** a Postgres session-level advisory lock (`pg_try_advisory_lock`) held on a dedicated `pg` connection for the whole run. A second trigger records a run with status `SKIPPED_LOCKED` and exits.
- **Snapshot date:** `snapshot_date` = IST date of the run − 1 day. A call at 00:30 IST covers roughly the previous day. This is one well-tested function.
- **Data window:** each run stores `window_start` (call time − 24 h) and `window_end` (call time) so shifted windows are visible.
- **Idempotency:** re-running for the same `snapshot_date` + pull **replaces** that pull's metric rows (delete + insert in one transaction). It never duplicates them.
- **Order per pull:** (1) call the API, (2) store the raw JSON, (3) parse and flatten, (4) write the metrics.
- **Reprocess:** if parsing fails, the raw response is kept. `npm run etl:reprocess -- --runId=...` (or the UI action) re-parses stored raw responses **without spending an API call**. It creates a new run with `trigger = REPROCESS`, `api_calls_used = 0` and `reprocess_of_run_id` pointing at the original.
- **Retries:**
  - Network errors and 5xx: up to 2 retries with exponential backoff. Each retry counts as an API call and is a separate step row (`attempt` 1..3).
  - **429: no retry** (`RATE_LIMITED`).
  - 401/403: no retry (`AUTH_ERROR`).
  - 400: no retry (`BAD_REQUEST`).
- **Timeouts:** 60 s per request (`TIMEOUT`).
- **Run status:** `RUNNING`, `SUCCESS` (all enabled pulls OK), `PARTIAL_SUCCESS` (some pulls failed or were skipped), `FAILED`, `SKIPPED_LOCKED`.
- **Error codes:** `AUTH_ERROR`, `RATE_LIMITED`, `BAD_REQUEST`, `NETWORK_ERROR`, `TIMEOUT`, `PARSE_ERROR`, `DB_ERROR`, `BUDGET_EXHAUSTED`, `UNKNOWN`.
- Each failure stores a human-readable `error_message` and a sanitized `error_details` (JSON: HTTP status, response snippet, stack). **The API token is never stored or logged.**
- **Stale run recovery:** at the start of each run, any run left `RUNNING` for more than 30 minutes is marked `FAILED` with `error_code = UNKNOWN` and the message "Run did not complete (process killed or timed out)".

### 4.5 Alerts

- On `FAILED` or `PARTIAL_SUCCESS`: notify via the optional **Microsoft Teams incoming webhook** (`TEAMS_WEBHOOK_URL`) and/or email (SMTP env vars).
- Content: status, snapshot date, failed pulls, error codes, a link to the run detail page, and **"Run a late run today before 00:30 IST tomorrow, or this day is lost"** with the remaining budget.
- Also alert when **no successful run in the last 26 hours**. Exposed as `npm run etl:health` so the host can cron it too.

### 4.6 Missed-day recovery (late run)

Replaces the backfill.

- If the 00:30 run fails, an admin triggers **Run now** later the **same IST day**. It uses `numOfDays=1` and may use the reserved calls.
- Its `snapshot_date` is still IST date − 1, so it fills the missing day. Its window is shifted (e.g. 10:00 → 10:00 instead of 00:30 → 00:30). This is accepted as close enough. The run detail page shows the window, and the dashboard completeness indicator marks such days as "late window".
- If nobody reruns before the next 00:30 run, that day is a permanent gap. It shows in red on `/runs` and in the dashboard completeness indicator.
- Raw responses are stored, so a smarter gap-recovery feature (deriving days from `numOfDays=2` calls) can be added later without schema changes to the core tables. **Out of scope for v1.**

## 5. Database schema (Prisma)

Table and column names are snake_case in Postgres (`@map`).

- **`pipeline_runs`**
  - `id` (uuid), `trigger` (`CRON_CLI` | `CRON_HTTP` | `MANUAL` | `REPROCESS`), `triggered_by` (email or `system`)
  - `status`, `snapshot_date` (date), `num_of_days` (always 1 in v1; kept for history), `window_start`, `window_end`
  - `reprocess_of_run_id` (nullable)
  - `started_at`, `ended_at`, `duration_ms`
  - `pulls_total`, `pulls_succeeded`, `pulls_failed`, `pulls_skipped`
  - `api_calls_used`, `rows_fetched` (raw `information` items), `metrics_written` (flattened rows)
  - `error_code`, `error_message`, `error_details` (jsonb), `created_at`
  - Indexes: (`started_at` desc), (`status`, `started_at`), (`snapshot_date`)
- **`pipeline_run_steps`** (one row per pull attempt)
  - `id`, `run_id` FK, `pull_key`, `dimensions` (text[]), `attempt`
  - `http_status`, `status` (`RUNNING` | `SUCCESS` | `FAILED` | `SKIPPED_BUDGET`), `started_at`, `ended_at`, `duration_ms`
  - `rows_fetched`, `metrics_written`, `error_code`, `error_message`, `error_details`
- **`raw_responses`**: `id`, `step_id` FK, `snapshot_date`, `pull_key`, `payload` (jsonb), `fetched_at`. Indexes on (`fetched_at`) for purging and (`snapshot_date`, `pull_key`).
- **`metric_values`** (long/narrow)
  - `id` (bigint), `snapshot_date` (date), `pull_key`, `metric_name`, `field`
  - `dim1_name`, `dim1_value`, `dim2_name`, `dim2_value`, `dim3_name`, `dim3_value`, all `NOT NULL DEFAULT ''`
  - `value` (numeric(20,6)), `run_id` FK, `created_at`
  - **Unique index** on (`snapshot_date`, `pull_key`, `metric_name`, `field`, `dim1_value`, `dim2_value`, `dim3_value`)
  - Indexes on (`snapshot_date`), (`metric_name`, `field`, `snapshot_date`), (`pull_key`, `snapshot_date`)
- **`api_call_log`**: `id`, `run_id`, `step_id`, `called_at`, `http_status`, `budget_date` (indexed)
- **`pull_configs`**: `key` (PK), `dimensions` (text[]), `enabled`, `display_order`, `updated_at`, `updated_by`
- **`kpi_definitions`**: maps dashboard KPIs to raw data
  - `key` (PK), `label`, `metric_name`, `field`, `unit` (`percent` | `count` | `seconds` | `minutes` | `ratio`)
  - `aggregation` (`weighted_avg` | `avg` | `sum` | `last`), `higher_is_better`, `display_order`, `updated_at`, `updated_by`
  - **`weighted_avg`** = `SUM(value × sessions) / SUM(sessions)`. `sessions` is `Traffic.totalSessionCount` for the **same snapshot date, pull and dimension values** (for the `url` pull, that URL's sessions). Days with no session count are excluded from both sums.
  - Seeded KPIs (all mappings must be confirmed against real data; see §12 checklist):

    | key | Label | metric / field | unit | aggregation | higher is better | confidence |
    |---|---|---|---|---|---|---|
    | `rage_clicks_pct` | Rage clicks % | `RageClickCount` / `sessionsWithMetricPercentage` | percent | weighted_avg | no | likely |
    | `dead_clicks_pct` | Dead clicks % | `DeadClickCount` / `sessionsWithMetricPercentage` | percent | weighted_avg | no | likely |
    | `quick_backs_pct` | Quick backs % | `QuickbackClick` / `sessionsWithMetricPercentage` | percent | weighted_avg | no | likely |
    | `js_errors_pct` | JavaScript errors % | `ScriptErrorCount` / `sessionsWithMetricPercentage` | percent | weighted_avg | no | likely |
    | `total_sessions` | Total sessions | `Traffic` / `totalSessionCount` | count | sum | yes | confirmed |
    | `pages_per_session` | Avg pages per session | `Traffic` / `pagesPerSessionPercentage` | ratio | weighted_avg | yes | confirmed |
    | `scroll_depth` | Avg scroll depth % | `ScrollDepth` / `averageScrollDepth` | percent | weighted_avg | yes | **guess** |
    | `session_duration` | Avg session duration | `EngagementTime` / `totalTime` (or `activeTime`) | seconds | weighted_avg | yes | **guess** |

- **View `v_daily_kpis`** (raw SQL migration): one row per `snapshot_date` from the `overall` pull, one column per seeded KPI key, built with `MAX(value) FILTER (WHERE kd.key = '…')` joined to `kpi_definitions` on (`metric_name`, `field`). Mapping edits in Settings flow through without a migration. For the dashboard and future Power BI / Fabric use.

## 6. Authentication & authorization

- **Auth.js v5** with the **Microsoft Entra ID** provider, JWT sessions (no user tables).
  - Env: `AUTH_MICROSOFT_ENTRA_ID_ID`, `AUTH_MICROSOFT_ENTRA_ID_SECRET`, `AUTH_MICROSOFT_ENTRA_ID_ISSUER` (tenant-specific, so **only our tenant** can sign in), `AUTH_SECRET`.
- All pages and API routes require a session, **except** `POST /api/etl/run` with a valid `CRON_SECRET` and `GET /api/health`.
- **Roles:**
  - `admin`: manual runs, reprocess, edit KPI mappings and pull configs.
  - `viewer`: read-only.
  - Resolved at sign-in from the Entra `roles` claim (app roles `admin`/`viewer`) or group membership if present. Otherwise from env allowlists `ADMIN_EMAILS`, `VIEWER_EMAILS`, or `ALLOWED_EMAIL_DOMAIN=codebasics.io` (viewer).
- Header shows the user's name, avatar and a sign-out button.

## 7. UI requirements

Clean, minimal layout with a sidebar: **Dashboard**, **Pipeline Runs**, **Settings** (admin only). Light and dark mode. Works on a laptop and stays readable on mobile. `Asia/Kolkata` everywhere, with the timezone label on timestamps.

### 7.1 Pipeline Runs (`/runs`)

- **Summary strip:**
  - last run status and time,
  - next scheduled run (from `CRON_SCHEDULE`, human-readable),
  - success rate over the last 30 runs,
  - **API calls used today / budget**,
  - days with **no successful data** in the last 30 days (red: permanent gaps once past the same-day recovery point).
- **Table columns:** Run ID (short), Trigger, Status (coloured badge), Snapshot date, **Start time**, **End time**, Duration, **Data retrieved** (rows fetched / metrics written), API calls used, **Failure reason** (error code + truncated message; full text in a tooltip).
- **Filters:** status, trigger, date range. Newest first, server-side pagination.
- **Admin actions:**
  - **Run now**: confirmation dialog shows remaining API budget, which pulls will run, and a warning when reserved calls will be used.
  - **Reprocess** on runs with parse failures.
- Auto-refresh every 15 s while any run is `RUNNING`.

### 7.2 Run detail (`/runs/[id]`)

- Header: all run fields, including the data window and, for reprocess runs, a link to the original run.
- Step table per pull attempt: dimensions, attempt, HTTP status, duration, rows, metrics written, error.
- Expandable **error details** (sanitized JSON) and **raw response preview** (first ~200 lines, download-as-JSON button).

### 7.3 Dashboard (`/dashboard`)

- **Period selector:** Latest snapshot, Last 7 / 30 / 90 days, This month, Last month, Custom range. Persisted in URL query params.
- **KPI cards** (one per KPI definition, Clarity weekly email style):
  - Big value for the period using the KPI's aggregation (session-weighted for rates and averages).
  - **% change vs. the previous equivalent period**, green when good and red when bad per `higher_is_better`.
  - Small sparkline.
- **Data completeness indicator:** "28 of 30 days have data", listing missing dates and days collected by a late run.
- **Main line chart:**
  - Metric multi-select (up to 4), dual Y-axis when units differ.
  - Dimension filter: None / Device / Source / Medium / URL. With a dimension, pick up to 5 values (default top 5 by sessions), one line per value, single metric.
  - Granularity: Daily / Weekly / Monthly. Weekly and monthly buckets use the KPI's aggregation (session-weighted where applicable).
  - Optional 7-day moving average.
  - Missing days are **breaks in the line**, not zeros.
  - Tooltip: date, value and unit for every series.
  - "Download CSV" for the data shown.
- **Top frustration pages** (from the `url` pull, period-weighted by sessions): URL, sessions, dead click %, rage click %, quick back %, JS error %. Sortable.
- **Pipeline health mini-panel:** last run status and a link to `/runs`.
- Empty and loading states everywhere. With no data yet, a friendly empty state explains the first run is pending.

### 7.4 Settings (`/settings`, admin only)

- View and toggle pull configs. Show estimated API calls per scheduled run against the budget; block saving if scheduled usage would exceed `budget − reserved`.
- Edit KPI definitions (label, metric/field mapping, unit, aggregation, `higher_is_better`).
- **Discovered fields:** distinct (`metric_name`, `field`) pairs seen in the data.
- Token status: only whether `CLARITY_API_TOKEN` is set and the HTTP status of the most recent call. **Never display the token.**

## 8. API routes (session-protected unless noted)

- `POST /api/etl/run`: cron trigger (`CRON_SECRET`, no session), or manual trigger with an admin session
- `GET /api/runs`, `GET /api/runs/[id]`, `GET /api/runs/[id]/raw` (JSON download)
- `POST /api/runs/[id]/reprocess` (admin)
- `GET /api/metrics/kpis?from&to`: KPI values for the period and the previous period
- `GET /api/metrics/timeseries?metrics[]&dimension&values[]&from&to&granularity`
- `GET /api/metrics/dimension-values?dimension&from&to`: top values by sessions
- `GET /api/metrics/top-pages?from&to`
- `GET /api/health` (no auth): DB connectivity and last successful run time; **503** if no success in 26 h

Every query parameter is validated with Zod. Heavy aggregation (including weighted averages) runs in SQL.

## 10. Non-functional requirements

- **Security:**
  - Token only in env/secret storage; redacted in all logs and errors.
  - Constant-time comparison for `CRON_SECRET`.
  - Security headers set.
  - URL dimension values: query strings stripped (`STRIP_URL_QUERY=true`), then capped at **2,000 characters** so they stay within Postgres index limits.
- **Observability:** structured logs with `runId` on every ETL log line.
- **Performance:** dashboard API responses under 500 ms for 1 year of data, backed by the indexes in §5.
- **Data retention:** `metric_values` kept forever; `raw_responses` kept for `RAW_RETENTION_DAYS` (default 180), purged by `npm run etl:purge-raw`.
- **Code quality:** ETL core in `src/etl/`, pure and testable, HTTP client injected. ESLint + Prettier. No `any` in ETL code.

## 15. Decisions log

| Date | Decision | Reason |
|---|---|---|
| 2026-11-25 | Standalone repo under the product owner's account | Different stack from `lms-web` (Laravel/MySQL). |
